# Spec — a synthetic training-corpus factory for the five role profiles

Status: spec, not implemented. No source change and no corpus is authorised by this file.
Scope: how the five per-role corpora are authored, what a row is, what the factory must
prove about a corpus before a fine-tune may start, and how the corpus is split.
Out of scope: the grammars themselves (`role-grammars.md`), training, adapters, metrics
(`task-reframing.md`), and the mined archive (untouched).

---

## 0. The decision this spec records

**The five role corpora are authored, not mined.** Five role profiles — human-interfacer,
orchestrator, worker, fetch-worker, search-worker — each get their own grammar, their own
state schema, and their own corpus, generated by subagents under a protocol with a
machine-checkable invariant set. Nothing in `mine/` supplies a training row, and the mined
archive stays exactly where it is: frozen, quoted, and no longer the training source.

Two reasons, both measured and both fatal to mining as the primary source:

1. The mined population is censored to one class (`negative-sampling.md` §1: 524 `nudge` /
   3 `leave` / 0 / 0). A row exists only because a human spoke, so P(human intervened | row)
   = 1 by construction. No filter over that population produces a corpus a supervisor can
   learn from.
2. The mined renderer leaked the label into the input (`task-reframing.md` §1.4 D1,
   `dataset.ts:174-175`). A population that is 99.43% one class cannot expose that leak
   as a leak; it looks like accuracy. Synthetic generation is the point at which we get to
   decide the joint distribution of (state, label), so it is the point at which the leak is
   either designed out or reproduced.

**What this spec consumes.** `docs/specs/role-grammars.md` is the authority for each
profile's grammar, state schema, allowed value space, renderer and system text. This
document defines only (a) the machine-readable descriptor the factory reads, and (b) what
the factory does with it. **No grammar, state field, tool, op name or allowed value is
invented here.** If the descriptor is missing for a profile, the factory exits with an
error; it never falls back to a default grammar.

**Where the numbers come from.** Every constant below is either measured on this machine
(§4 step time, §8 token budget) or derived from a table in the two sibling specs, and is
cited at the point of use. Nothing here is estimated silently.

## 1. The two failures, stated exactly, and the four rules that follow

### 1.1 Failure one — a single-class corpus, and the baseline that made it invisible

`mine/out/decision-points.jsonl` holds 527 rows. Through `LABEL_TO_OP` they are 524
`nudge`, 3 `leave`, 0 `flag`, 0 `declare_done` (`negative-sampling.md` §1). Majority
baseline 99.43%, expected regret of `always nudge` 0.028/task. The corpus's own metronome
was simultaneously the accuracy optimum and the regret optimum (`task-reframing.md` §1.5),
so no scorer over it could separate a supervisor from a constant.

The instructive part is not the ratio, it is what the ratio hid: the two ops a supervisor
actually needs to be right about — stay quiet, escalate — had 3 and 0 rows. A corpus is not
"small" or "large"; it is *supported* or *unsupported* per class.

**Rule 1 (from failure one).** A corpus is admitted only with a per-op floor and a class
balance band, and the majority baseline is printed as a gate number, not a footnote.

### 1.2 Failure two — one field carrying the answer

`finetune/dataset.ts:174-175` (`decisionInput`), verbatim:

```ts
status: point.humanText ? "working" : "idle",
intent: point.humanText.length <= humanCap ? point.humanText : `${cutPrefix(point.humanText, humanCap)}…`,
```

`leave` rows have `humanText === ""` (the whole point of a `leave` point is that no human
spoke), so the two live classes rendered as:

| | `status` | `intent` |
|---|---|---|
| `nudge` | `working` | the human's next message |
| `leave` | `idle` | empty |

Two classes, separable by one enumerated field with zero reasoning. A 121M attention-only
model would learn `intent == "" ⇒ leave` in the first epoch and learn nothing else. This
is also why `task-reframing.md` §4.1 V6 exists: the gate is a gate, not a style rule.

**Rule 2 (from failure two).** No single field, and no single enumerated value of a field,
may determine the label beyond a stated threshold. The check is a classifier run per field
and it has numbers (§5, I3).

### 1.3 Two more, from the same two documents

- The 3 `leave` rows were three copies of one token (`task-reframing.md` §1.2 D3: all three
  `humanText == "cancel"`, in three consecutive sessions, same cwd) — and a zero-row class
  is a sink rather than an absence (`d8` emitted `declare_done` 30/50 times against one,
  scoring 0.06 against a 0.81 baseline). Both are the same defect: a class whose support is
  a formality. → **Rule 3: distinctness is per-class and every op in the catalogue carries
  the full allocation, or the op leaves the catalogue** (§5 I1, I5).
- `d20` was scored on `d4`'s val set (`task-reframing.md` §5.1). → **Rule 4: every corpus
  writes its own `valSha`, and a rung is scored on the val of the corpus it was trained
  on** (§7).

## 2. The five profiles, and the descriptor contract

### 2.1 What a profile is

A profile is the tuple

```
Profile = (name, system, tools[], state[], render, argumentRules, lexicon)
```

- `system` — the profile's system prompt, from `role-grammars.md`. One per profile, never
  shared: the grammar differs, so the text that describes it differs.
- `tools[]` — `{name, description, argument}`. `name` is the op label. `argument` is the
  single argument's name. This is the whole answer space of the profile:
  `Y_profile = set(tool.name)`.
- `state[]` — ordered field list: `{field, type, space, rendered, constraints}`. `type ∈
  {enum, int, bool, text}`, `space` is the enumeration or `{min,max}` for ints or a char
  cap for text, `rendered` says whether the field appears in the query, `constraints` are
  the field's own rules (what makes a value legal given another field's value).
- `render` — the order and format the state is rendered in, so the query is built from the
  descriptor rather than from a hand-written string per profile.
- `argumentRules` — per op: `minChars`, `maxChars`, and where the argument must come from
  (e.g. an op whose argument must name the resource it operates on). These are what make
  "the argument is a span of the state" a real constraint on generation rather than a
  post-hoc filter.
- `lexicon` — the forbidden tokens for this profile (see §3.2 blindness and §5 I7).
- `evidence` / `context` — the field partition, and it is required, not advisory. `evidence`
  is the set of fields the op is **supposed** to be read from: the pane's own account of
  what it did and where it stopped. `context` is everything the op must **not** be readable
  from on its own: ids, status, tick counters, lengths, timestamps, session and cwd. The
  partition exists because two sibling specs need opposite things from the same check
  (`hi-orchestrator.md` §0 claim 4, §8.4: for the HI the target is a span *of the input*, so
  "the label is in the input" is the task and not a leak), while the historical failure
  (§1.2) was a **context** field carrying the answer. §5 I3 gates on `context` and on the
  lexical layer; it cannot gate on `evidence` without forbidding selection tasks outright.

### 2.2 The descriptor file the factory reads

`role-grammars.md` is prose. The factory needs the machine form, so it reads:

```
docs/specs/role-grammars.json      (or one fenced ``json`` block per profile inside the .md)
{
  "profiles": [
    {
      "profile": "fetch-worker",
      "system": "…",
      "render": ["status", "claim.state", "phase", "last", "tail"],
      "tools": [{"name": "…", "description": "…", "argument": "…"}, …],
      "state": [{"field": "status", "type": "enum", "space": ["…"], "rendered": true, "constraints": "…"}, …],
      "argumentRules": {"<op>": {"minChars": 8, "maxChars": 140, "mustContain": ["<field>"]}},
      "evidence": ["last", "tail"],
      "context": ["pane", "cwd", "status", "phase", "idleTicks"],
      "lexicon": {"forbidden": ["nudge", "leave", "flag", "declare_done", "…"]}
    }, …
  ]
}
```

Required, and refused if absent: **for each profile, `tools` must be a non-empty list with
distinct names; each `tools[i].argument` must be non-empty; every `rendered` field must have
a `space`; and `k = |tools|` must be documented** (§4 needs it). The factory validates the
descriptor before a single row is generated and writes the descriptor's `sha256` into every
corpus manifest, so a corpus is always traceable to the grammar it was authored against.

`evidence ∪ context` must cover every `rendered` field, disjointly, and `context` must
contain `status`, the tick/idle counters, every id, every length, and the cwd — those are
declared context by fiat because they are the fields §1.2's leak lived in and a profile
that wants one of them as evidence has to argue it in `role-grammars.md` first.

### 2.3 The factory will not run without it

There is no default grammar, no "start with four ops like the mined one", and no shared
state schema across profiles. Two profiles with the same op names but different argument
rules are different corpora and may not be pooled — §5 I1's floors are per profile, and a
pooled corpus hides a starved op behind a well-fed one.

## 3. The generation protocol

### 3.1 Why subagents, and what that costs

A template engine over the state schema would satisfy every format invariant and fail I1
by construction: the state space is open-ended text (tails, `last`, titles), so any
generator that enumerates produces a phrasebook, and a phrasebook is memorizable by
1-NN (§6 M5). Subagents write prose that varies the way a real pane varies.

The cost is that subagents are slow, expensive, and non-deterministic, so the protocol is
built to be (a) batched, (b) blind, (c) cross-checked, and (d) reproducible by seed. None
of that is optional; a factory that trusts one model's unilateral judgement produces a
corpus that is a portrait of that model's priors, which is the bias §6 exists to price.

### 3.2 Three stages, and the blindness rule

Three distinct subagent roles, in order. Each is a fresh conversation with no sight of the
others' prompts.

| stage | receives | emits | temperature |
|---|---|---|---|
| **state-author** | profile name + purpose, `state[]`, `render`, the seed batch, the co-occurrence constraints | one state object per seed, schema field order | 1.0 |
| **labeller** | `tools[]` (names + descriptions + argument names), the **rendered state block only**, the answer contract | `{op, argument, rationale}` or `{reroll: "no-equivalent-span"}` | 0.0 |
| **adversary** | `tools[]`, the rendered state block, the labeller's call — **not** the rationale, **not** the seed | `{verdict: unambiguous\|ambiguous\|wrong, reason}` | 0.0 |

**The blindness rule, which is the whole design:**

> The state-author is never given `tools[]`. The labeller is never given the seed, the
> intended op, the region, the rationale of any other row, or the acceptance thresholds.

The state-author writes a pane, not an answer. If it knew the op vocabulary it would write
states that announce their own answer, and the corpus would encode "the state says which op
it wants" — a leak of the same family as §1.2, one level up.

Consequence, stated so nobody "fixes" it: **the state-author cannot be told what balance to
aim for.** Balance is not a property the generator controls; it is a property the *seed
pool* controls (§3.5), and it is enforced by rejecting rows, never by relabelling them.

### 3.3 The packets

Every call is one batch and one packet, in the repo's six-section delegation shape, so a
reviewer can diff a packet against the spec:

```
TASK            Author B states for profile <p>, one per seed, schema order, nothing else.
EXPECTED OUTCOME  A JSON array of B objects; each has exactly the fields in state[], in
                 order, each value legal per space[] and the co-occurrence constraints.
REQUIRED TOOLS   none — the profile has no tools; write prose, do not call anything.
MUST DO          vary tail content, wording, length and numeric values across the batch;
                 respect every constraint; keep every text field within its cap; make the
                 tail a plausible tail of a real pane in this role.
MUST NOT DO      do not name or imply an operation, a decision, a supervisor, a label, or
                 a course of action; do not reuse another row's phrasing; do not use any
                 token in lexicon.forbidden; do not emit markdown; do not explain.
CONTEXT          <profile purpose>, <state schema verbatim>, <render order>,
                 <seed batch: seedId + region + prose>, <the 5 most recent accepted states
                 for this profile, for evasive variety>
```

The `MUST DO` line about variation and the `MUST NOT DO` line about op words are both
load-bearing: the first is what I1 measures, the second is what keeps the state from
narrating the label. The `CONTEXT` tail of recent accepted states exists so a batch of 24
does not read as 24 variants of one sentence.

The labeller's packet is the smallest one in the system:

```
TASK            One pane state from the <p> profile. Emit the one call a supervisor should make.
EXPECTED OUTCOME  {"op": <one of tools[].name>, "argument": "<span quoted from the state>",
                  "rationale": "<one clause, >= 8 words, naming the evidence>"}
                  or {"reroll": "no-equivalent-span"}.
MUST DO          quote the argument verbatim from the state, 8..140 chars, no ellipsis;
                 if no span of the state could be sent as this call's argument, reroll.
MUST NOT DO      do not invent text the state does not contain; do not reason about the
                 corpus, the generator, or the scoring; do not emit more than one call.
CONTEXT          <tools[] verbatim>, <the rendered state block>
```

### 3.4 What a row is

`rows.jsonl`, one object per line, the authored record and the factory's unit:

```json
{"rowId":"sha256:…",
 "profile":"fetch-worker","seedId":"fw-0042","region":"throttled-with-budget",
 "state":{"status":"working","phase":"retry","attempt":2,"last":"fetch_items","tail":"…"},
 "renderedState":"status: working\nphase: retry\nattempt: 2\nlast completed: fetch_items\nterminal tail:\nfetch_items: GET https://api.example/v2/items -> 429 rate limited; retry budget 1 of 3 left",
 "call":{"op":"retry_fetch","argument":"GET https://api.example/v2/items -> 429 rate limited"},
 "rationale":"throttled twice with a retry budget left, so the fetch is retryable",
 "templateId":"get @ -> # rate limited",
 "pairId":"fw-0042-a",
 "provenance":{"stateModel":"…","labelModel":"…","advModel":"…","promptSha":"…","at":"…"},
 "verdict":{"adversary":"unambiguous","reason":"…"}}
```

The example is written so I4 is visibly satisfied: `call.argument` is a byte substring of
`renderedState`, and `templateId` is that argument put through §5 I1's `normalizeArg`
verbatim — lowercased, the URL collapsed to `@`, the status code to `#`.

- `renderedState` is the **exact bytes** the renderer produced, stored rather than
  recomputed. Every check in §5 reads it, so a check and the trainer cannot disagree about
  what the state was.
- `rowId = sha256(profile ‖ "\0" ‖ renderedState ‖ "\0" ‖ op)`. Content-addressed, so a
  regeneration that changes a byte changes the id, and `valSha` cannot silently point at a
  stale split.
- `templateId` is the argument's normalized skeleton (§5 I1 defines the normalization
  exactly). It is emitted, not inferred, because inferring it later means two
  implementations of "template".
- `pairId` marks a minimal-pair member; both members carry the same `pairId` and the same
  `seedId`, which is what makes the group-aware split (§7) and the Jaccard exemption (§5
  I5) possible.

Rejects go to `rejects.jsonl` with a reason, never deleted. A reject is data about the
generator, and §6's numbers are computed from them.

### 3.5 Seeds, regions, and how balance happens without telling the labeller

A **seed** is `{seedId, region, prose}`: a situation in the world — what the pane was
asked to do, what just happened — with no operation named. A **region** is a labelled
slice of the situation space (e.g. `healthy-progress`, `blocked-on-permission`,
`throttled-with-budget`, `done-and-reported`, `ambiguous-partial`). Regions exist so the
factory can allocate *situations*, which it is allowed to do, instead of *labels*, which it
is not.

The loop:

```
for each profile:
  seedPool ← generated once, ≥ 2.5 × R seeds, regions allocated evenly across the regions
             that role-grammars.md declares for the profile
  while |accepted| < R:
     batch ← 24 seeds, drawn round-robin across regions, weight = deficit in the
             currently-rarest op after the last complete round
     states ← state-author(batch)
     for each state:
        call ← labeller(state)
        if call.reroll: reject("no-equivalent-span"); continue
        verdict ← adversary(state, call)
        if verdict != unambiguous: reject(verdict.reason); continue
        if violates I1..I8 pre-check: reject(invariant id); continue
        accept(row)
```

Balance is emergent and then corrected by allocation: the seed-region mix determines the
op mix, the observed deficit reweights the next batch, and a row is never relabelled to
fill a class. If the factory cannot fill an op to its floor after the seed pool is
exhausted, that is a **grammar finding** — the op is not distinguishable from the others
in this profile's state space — and it is reported as such (§9), not fixed by generation.

### 3.6 Rerolls, rejects, and their caps

| reason | meaning | cap before the profile is rejected |
|---|---|---|
| `no-equivalent-span` | the state contains no span usable as the argument | ≤ 20% of states |
| `adversary:ambiguous` | an expert could not decide from the state alone | ≤ 10% |
| `adversary:wrong` | the call contradicts the state | ≤ 5% |
| `invariant:<id>` | caught by a deterministic pre-check | ≤ 10% |

A `no-equivalent-span` rate above 20% is the state-author's fault (it is writing panes with
nothing usable to say) or the grammar's (the argument rule is impossible for that op). Both
are fixable only upstream, so the factory stops rather than grinding.

### 3.7 Determinism and provenance

- The labeller and adversary run at temperature 0. A 5% random sample is re-labelled a
  second time; **disagreement on that sample above 2% fails the profile** — an op whose
  labels flap under an unchanged prompt is not a learnable class, and no number computed
  from it means anything.
- `promptSha = sha256(canonicalized packet template)`. Packets are templates with fixed
  text; the varying parts are the seeds and the states. A template edit changes
  `promptSha`, which changes `corpusSha`, which is how a reader knows two corpora were not
  generated the same way.
- Every row carries the three model identities. A corpus generated by one model for all
  three stages is flagged in the manifest as `independence: "single-model"` and may not be
  quoted as cross-validated (§6 M4).

### 3.8 Batching and call counts

Batch size `B = 24`. With `R = C·k` (§4.1) and a 15% reject allowance, the acceptance pass
needs roughly `R/0.85` attempts:

| k | R | attempts | state-author | labeller | adversary | total calls |
|---|---|---|---|---|---|---|
| 3 | 480 | 565 | 24 | 24 | 565 (per state) | 613 |
| 4 | 640 | 753 | 32 | 32 | 753 | 817 |
| 5 | 800 | 942 | 40 | 40 | 942 | 1022 |

The labeller is batched over a whole batch's states (24 per call), so it matches the
state-author count; the adversary is per row because its job is to be a second opinion on
that row, and batching it would let one verdict cover 24 rows. Five profiles ≈ 4,000 calls
and ≈ 4,000 rows attempted for ≈ 3,400 accepted. That is the cost of a corpus that is not
a phrasebook, and it is stated here so nobody discovers it later.

**No subagent is in the acceptance path.** The adversary is a per-row filter whose rate is
a published number; every gate in §9 is deterministic code over `rows.jsonl`.

## 4. The row plan, and why 160 per op

### 4.1 The plan, in three bands

```
C_target = 160      rows per op, train + val combined — §4.2's four floors
C_min    = 100      below this the val cannot carry V4's n_k ≥ 20 (§4.2 F1)
R_budget = the row count the wall clock allows — §4.3, measured, not chosen
vf       = 0.20     val fraction

C = min(C_target, floor(R_budget / k))          k = |tools| from the descriptor
R = C · k
```

The three outcomes, and they are the only three:

| C | meaning | consequence |
|---|---|---|
| `C ≥ 100` | the profile is trainable at the resolution §4.2 buys | full §9 gate; `resolution: "0.60-vs-0.50"` when `C ≥ 150`, `provisional` below it |
| `40 ≤ C < 100` | the catalogue is too wide for the box at a usable resolution | the profile may be **generated and audited but not trained**: it is a candidate, and §4.4 names the three routes out |
| `C < 40` | the op cannot carry a class | the op comes out of the catalogue (both the rows and the tool list: `AGENTS.md`, `slate.json` `triage`). Recompute `k`. |

| k | C | bound by | R | val | val/op | train/op |
|---|---|---|---|---|---|---|
| 3 | 160 | target | 480 | 96 | 32 | 128 |
| 4 | 160 | target | 640 | 128 | 32 | 128 |
| 5 | 160 | target | 800 | 160 | 32 | 128 |
| 8 | 108 | budget (`R_budget = 864`) | 864 | 173 | 21 | 86 |

`R_budget = 864` is what 12 epochs of 24 h buys at the trimmed step time (§4.3) — 54 steps.
A 5-op profile spends 21.9 of those 24 h, so k ≤ 5 is the range where §4.2's floor survives
intact; at k = 8 the val is 21/op, which clears V4's `n_k ≥ 20` by one row and is therefore
`provisional`. Anything wider than 8 ops cannot meet the floor at all and is generated as a
candidate without a fine-tune (§4.4). At the *untrimmed* step time `R_budget` is 432, which
leaves only k ≤ 2 at the target — which is the concrete form of the statement that the
prefix trim is a precondition of this factory rather than an optimisation.

### 4.2 The justification, against "~450 was already marginal for a 4-class problem"

That reading of the old corpus is wrong in a way that matters, and the wrongness is what
sets the number. 452 rows over 4 ops was not "113 per class and marginal". It was 131
`nudge`, 0.75 `leave`, 0 `flag`, 0 `declare_done` — the ops with the interesting boundaries
had zero or near-zero support. So "450 was marginal" is not evidence that ~113/class is too
few; it is evidence that *support per op* is the quantity, and the old corpus did not have
it. `C` is therefore fixed by four independent floors, and taken as the max:

| floor | argument | implies |
|---|---|---|
| **F1 — resolution** | `task-reframing.md` §4.8: `n_leave ≥ 20` for a non-provisional eval set (V4), and `n_k = 30` gives a BA interval of ±0.11, which resolves 0.60-vs-0.50 and nothing finer. At `vf = 0.20`, 30 val rows/op needs 150 rows/op. | **150** |
| **F2 — template diversity** | §5 I1 requires ≥ 10 distinct argument structures per op with no single structure above 20% of the op. To give each of 10 structures ≥ 8 rows: 80. The 20% cap alone implies 50. | 80 |
| **F3 — boundary** | §6 M2 requires ≥ 12 admitted minimal pairs per op, two members each (24 rows), plus the neighbour families they belong to (≥ 16 more). | 40 |
| **F4 — observed learnability** | The only archive that learned any surface feature is `control-d8`, whose `flag` recall ran 0.86–1.00 across three re-runs on 89 `flag` rows — i.e. this architecture starts selecting surface evidence at ~100 rows/op and not below. 160 is that with 60% margin. | 100 |

`C = max(150, 80, 40, 100) = 160`. The rounding is upward on F1 because F1 is the only floor
that is a *statistic* rather than a design choice, and a val of exactly 30/op leaves no room
for a single row to be dropped at conversion time.

**Why not larger.** F1's finer resolution — `n_k ≥ 60`, `task-reframing.md` §4.8's floor for
"any claim finer than beats the metronome" — needs 300 rows/op, i.e. 1,500 rows at k=5, which
books 82 h per profile at the measured step time (41 h post-trim) against a 24 h gate. The
wall clock forbids it, so the factory accepts ±0.11 and **states it**: each manifest carries
`resolution` and no finer claim may be made from that profile's val. That is a recorded
trade, not an oversight.

### 4.3 The wall clock, which is the binding constraint on the whole factory

Measured on this box (`AGENTS.md`, `docs/specs/2026-10-26-agent-fleet-design.md`): **262.4
s/step**, batch 16, seq 1024, **126.8 min/epoch** at 452 rows (29 steps). So

```
h/epoch  = ceil(R/16) · t_step / 3600          t_step = 262.4 s measured
h/total  = 12 · h/epoch                        SLATE_EPOCHS = 12 (finetune/Makefile)
```

| k | R | steps | h/epoch | 12 epochs | 12 epochs at the documented ~2× trim |
|---|---|---|---|---|---|
| 3 | 480 | 30 | 2.19 | 26.2 h | **13.1 h** |
| 4 | 640 | 40 | 2.92 | 35.0 h | **17.5 h** |
| 5 | 800 | 50 | 3.64 | 43.7 h | **21.9 h** |
| 8 | 864 | 54 | 3.94 | 47.2 h | **23.6 h** |

The trim is the repo's own lever, already documented in `AGENTS.md`: of ~2,200 characters
per example, ~1,488 are the byte-identical system text plus tool schemas, and trimming it
gets `fit_max_len` from 1024 to 512 and "roughly halves step time". It is *cheaper* for
these corpora than for the mined one, because a role's grammar is smaller than the four-op
one and its state block is bounded by `render`.

**Budget gate.** A profile may be trained only when `12 · ceil(R/16) · t_step ≤ 24 h`, with
`t_step` measured by `finetune/slate.py probe` **on that profile's own train file** — not
copied from the 452-row number, because the sequence length follows the profile's prefix.
If the probe fails the gate:

1. set `--max-len` to the smallest power of two ≥ p95(prompt+target tokens)+8 (§8.3), which
   is where the ~2× comes from, and re-probe;
2. if still over, run 8 epochs and record `epochsOverride` with the probe numbers;
3. if still over, **the profile is not trainable on this box** — say so and stop. Do not
   shrink `C`: a corpus under the F1 floor is not a cheaper corpus, it is an unmeasurable
   one (§4.2).

Five profiles at k = (5, 5, 4, 4, 3) — arithmetic only, not a grammar claim — is 3,360 rows
and **91.9 h** post-trim (183.6 h pre-trim), i.e. one profile per night for five nights. That
is the same order as the ~100 h slate the repo has already accepted, and it is the reason
`C` is not larger.

### 4.4 Wide catalogues, and the one arithmetic conflict with `hi-orchestrator.md`

Three of the five roles are plausibly small-`k` (worker, fetch-worker, search-worker: a few
tools each). Two are not obviously so. `hi-orchestrator.md` §8.5 targets **640 rows for the
HI at 15 slots × 10 kinds**, and 400 for the orchestrator at 10 actions; this spec's floor
wants 160 rows *per op*. Run the §4.1 formula on the sibling's own number and the answer is
uncomfortable but mechanical:

```
k = 15, R = 640  →  C = 42 per op  →  val ≈ 8 per op  →  V4's n_k ≥ 20 FAILS  →  provisional
```

So a 15-op HI corpus at 640 rows **cannot** support a per-op claim, and no amount of
generation quality changes that — it is a statistic, not a defect. There are exactly three
ways out, and choosing one is a `role-grammars.md` decision that this spec requires be made
explicitly before the HI corpus is authored:

| option | what it costs | what it buys |
|---|---|---|
| **collapse the slots** to `k ≤ 7` and split the rest into a second profile with its own corpus | two corpora, two fine-tunes (~2× the wall clock), two `valSha`s | `C ≥ 125`, `resolution: "0.60-vs-0.50"`, per-slot claims allowed |
| **accept `provisional`** at k = 15 | no per-op claim may be quoted; the eval reports support and refuses recall (V4); the sibling's own "aggregate accuracy may not be quoted" then leaves almost nothing reportable | one cheap corpus, and a corpus that measures only whether *anything* was learned |
| **generate and audit, do not train** | the corpus is a candidate with a full §5 report | a grammar finding (which slots are distinguishable from the states at all) with no training spend |

The same arithmetic applies to the orchestrator at `k = 10` (`C = 86`, `provisional`) if
`R` stays at the sibling's 400. The factory does not resolve this; it refuses to author a
corpus whose `C` is undecided between those three, and `corpus check` prints `C`, the
implied val/op, and which of the three bands §4.1 puts the profile in *before* the first
seed is drawn. A profile that lands in the middle band is generated, audited, and marked
`train: false` — visible in the slate rather than discovered at hour 40.

Also stated plainly, because it is the one place this spec contradicts a sibling:
`hi-orchestrator.md` §8.6 sources rows from **mined human↔agent turns, plus synthetic rows
only where a cell would otherwise be empty**, and it argues that a 100%-synthetic cell "has
never met a human". This spec's remit is the other way round, and the reason is §1.1: the
mined population is censored to "a human spoke", which is exactly the censoring that produced
the 99.43% corpus, and it re-imports the leak through `dataset.ts:174-175` unless a second
renderer is maintained. A **mixed** corpus is defensible and is a third thing; it needs its
own spec, its own renderer-identity check, and its own provenance gate (mined rows must be
tagged and their per-cell fraction reported, per §8.6's own requirement). Until that spec
exists, no mined row enters `corpus/`.

## 5. The invariant set

Nine checks. `corpus check <profile>` runs all of them over `rows.jsonl` plus the derived
splits, writes `checks.json`, and exits non-zero if any gate fails. Every threshold is a
number in this section and a constant in the checker; none is tunable per corpus without
editing this spec.

Notation: `k = |tools|`, `n` = accepted rows, `n_c` = rows of op `c`, `T` = train side, `V`
= val side, `q = 1/k` = chance balanced accuracy.

### I1 — every tool is supported, and no single template saturates it

**Statement.** Each op has the full row allocation and its rows are structurally varied.

`C` is §4.1's per-op allocation: 160 unless the wall-clock budget binds, in which case it is
`floor(R_budget/k)` and the manifest says so. Every predicate below is stated in terms of
`C`, so a budget-bound profile is held to a floor rather than to a number it cannot reach.

**Predicates** (per op `c`, over `rows.jsonl`):

```
n_c ≥ C                         and   |{r ∈ T : op = c}| ≥ 0.8·C  and   |{r ∈ V : op = c}| ≥ 0.2·C
distinct { normalizeArg(r.argument) : op = c } ≥ 10
max over t of  #{op = c ∧ normalizeArg = t} / n_c ≤ 0.20
distinct { firstFourTokens(opener(r.renderedState)) : op = c } ≥ 5
distinct r.argument : op = c ≥ 40
```

`normalizeArg` is fixed here so two implementations agree: lowercase; replace every run of
digits with `#`; replace URL/path tokens (`https?://\S+`, `/[\w./-]+`, `[\w-]+\.[a-z]{2,4}`)
with `@`; collapse whitespace; strip terminal punctuation; keep the first 8 whitespace
tokens; join with a single space. `opener` is the first 4 whitespace tokens of the first
rendered line that is not a field header.

**Gate.** Any failure rejects the profile. A failing line names the op and, for the share
rule, the template that saturated it; the fix is more seeds in other regions — never
merging near-identical rows.

### I2 — class balance band, and a stated majority baseline

**Statement.** No op dominates, and no op is starved.

**Predicates:**

```
∀c:  0.80·q ≤ n_c/n ≤ 1.20·q                    (band)
∀c:  n_c/n ≤ 0.45                               (absolute cap)
majorityBaseline := max_c n_c/n                 (printed, and it IS the gate number)
```

With `C` rows per op this lands on `q` exactly: `majorityBaseline = 0.333 / 0.250 / 0.200` for
k = 3 / 4 / 5, and the corresponding exact-match floor is the same number. This is
deliberately the *opposite* of the deployment prior — a balanced corpus is what makes
balanced accuracy usable and what removes the metronome's advantage (§6 M5). The prior
itself is priced by `REGRET`, not by resampling.

**Gate.** Any op outside the band rejects the profile. Balance is never achieved by dropping
the majority's rows: the band is met by seed allocation (§3.5), and dropping rows is how the
mined corpus got into trouble.

### I3 — no single field determines the label

**Statement.** Five checks, because "the label is in the input" has five shapes: a field
sufficient on its own (the historical `intent`), an enumerated *value* sufficient
(`status: idle`), the field being empty in exactly one class (both at once), a *token*
sufficient (the `cancel` × 3 class), and a field whose removal collapses a competent
baseline (the multi-token version that no stump catches).

**Scope, which is the load-bearing half of this invariant.** I3a, I3b and I3e run on
`context` fields only — the partition §2.1 requires. A selection task where the op follows
from the evidence is the task, not a leak (`hi-orchestrator.md` §0 claim 4, §8.4). I3d runs
on **every** field, evidence included, because a single token carrying the label is a
shortcut whichever field it sits in, and that is the sibling's own "lexical stratum" reading
of its own leak. The historical failure is a `context` field, so it is caught either way.

**Predicate set.** The "field family" for a profile is, for each rendered field, both

- the field's **value** as text (TF-IDF, 2-gram, min_df=1), and
- the field's **emptiness** as a boolean, and

plus each of these pseudo-fields: `len(renderedState)` in deciles, `len(tail)` in deciles,
`tokenCount(renderedState)` in deciles, `idleTicks` bucketed into the profile's declared
buckets, and each `int` field bucketed. That is roughly 2.5× the field count and it is the
full set of one-field shortcuts a model could take.

**I3a — single-field sufficiency, on `context`.** For each member `f` of the field family
restricted to `context` fields:

```
BA_f = 5-fold stratified CV balanced accuracy, multinomial logistic regression on f alone,
       seed 0, no tuning                     # for enum/bool f: the optimal lookup table,
                                             # which is what the regression reduces to
require  BA_f ≤ q + 0.10
```

`q + 0.10` is the threshold: 0.433 at k=3, 0.35 at k=4, 0.30 at k=5. Balanced accuracy is
the metric, not accuracy, because accuracy re-rewards the majority and is exactly the
number that made the old corpus look fine.

**I3b — enumerated-value concentration, on `context`.** For every `context` field of
`type ∈ {enum, bool}` and every value `v` of it, and every op `c`:

```
support  := #{f = v ∧ op = c}  ≥ 12
precision := #{f = v ∧ op = c} / #{f = v}
recall    := #{f = v ∧ op = c} / n_c
fail if   precision ≥ 0.85 ∧ recall ≥ 0.15
```

On the historical leak this fires at `precision = 1.000, recall = 1.000` on (`intent` = `""`,
op `leave`) and on (`status` = `idle`, op `leave`), at support equal to the `leave` class.
I3b exists alongside I3a because a 5-class CV can dilute a perfect but small shortcut under
its own noise, while a rule is a rule; I3b names it in the failure message with the field,
the value and the counts.

**I3c — reported, not gated.** `max_f I(op; f)/H(op)` over the field family. Printed in
`checks.json` beside the gate numbers so a drift upward is visible between corpora even
while both pass. (A gate here would duplicate I3a with a less interpretable statistic.)

**I3d — lexical-token shortcut, on every field.** Over all fields, evidence included:

```
for every unigram and bigram t that occurs in renderedState:
    support   := #{t present ∧ op = c}  ≥ 12
    precision := #{t present ∧ op = c} / #{t present}
    recall    := #{t present ∧ op = c} / n_c
    fail if  precision ≥ 0.85 ∧ recall ≥ 0.15
```

This is the check the mined corpus would have failed on `cancel` → `leave` (3 rows, one
token, three sessions: `task-reframing.md` §1.2 D3) and it is `hi-orchestrator.md` §8.4's
bag-of-words stratum expressed as a corpus gate rather than an eval stratum. It is the one
place the gate reaches into `evidence`, deliberately: a single token is not evidence, it is a
shibboleth.

**I3e — ablation concentration, on `context`.** Fit the full-field baseline
(multinomial logistic regression over the whole field family, 5-fold CV) and record
`BA_all`. Then for each `context` field `f` refit without it:

```
fail if  BA_all − BA_(-f) ≥ 0.25      for any single context field f
```

I3e is the necessity test where I3a is the sufficiency test, and it catches the leak shape no
stump finds: a field whose *formula* encodes the label without being separable by any single
value (a status string that is a step function of the op, a tick count that is a monotone
function of it). `hi-orchestrator.md` §8.4 states this as "removing the label-bearing field
reduces accuracy to chance"; this is the corpus-time, model-free form of it. `BA_all` is also
printed as a ceiling diagnostic: if a linear model over all fields cannot get far above `q`,
the profile has no surface signal at all (§6 M5 G3's low side) and no fine-tune is worth
paying for.

**Gate.** Any I3a, I3b, I3d or I3e failure rejects the profile. Loosening any threshold is a
spec edit with a reason recorded here, not a per-corpus flag. An `evidence` field that trips
I3d is a corpus finding (the evidence is a shibboleth); an `evidence` field that trips I3a is
**not** a finding and is not measured.

### I4 — every argument is a span of the state

**Statement.** The engine's grounding gate suppresses a call whose argument is not a
substring of the query, and a suppressed call is a refusal (`task-reframing.md` §4.5, `s`).
A non-span row therefore teaches "refuse here", which is worse than teaching nothing.

**Predicates** (per row, byte-level on `renderedState`):

```
argument == argument.trim()
renderedState.includes(argument)                               # byte substring, zero tolerance
8 ≤ len(argument) ≤ 140                                        # matches ARGUMENT_CHARS=140
argument satisfies argumentRules[op]                           # minChars/maxChars/mustContain
len(argument.split(/\s+/)) ≥ 3
no lone surrogate in argument or renderedState                  # the tokenizer refuses them
                                                               # (dataset.ts::cutPrefix comment)
```

Plus, on the training target: `reasoning` is exactly `"<span>" -> <argname>` where
`<span>` ⊆ `renderedState` and `len(span) ≤ 60`, matching the format `dataset.ts` already
produces. The reasoning span is a span too, for the same reason.

**Gate.** One violation rejects the row before it is accepted; the profile is rejected if
more than 0.5% of *otherwise accepted* rows are non-span. Zero is the target and 0.5% is the
allowance for a checker/renderer disagreement, not for generation slop.

### I5 — no two rows share a `(label, state)` pair, and no class is one string

**Statement.** Distinctness, in three layers, because the mined corpus failed all three.

**Predicates** (over accepted rows):

```
L1  (op, renderedState) is unique                                     # the stated invariant
L2  renderedState is unique across ops                                # no contradictory labels
L3  for any two rows with different seedId:                           # the D3 killer
      charShingleJaccard(5, renderedState_a, renderedState_b) ≤ 0.85
L4  per op: distinct renderedState ≥ 0.95 · n_c
```

L3 is exempt for rows sharing `pairId` — minimal pairs are *supposed* to be near-identical,
and that is the point of them (§6 M2). L3 exists because `task-reframing.md` §1.2 D3's
`leave` class was three copies of the string `cancel`: a class that is one sentence
replicated teaches a token, not a decision. L4 is the per-class version of the same thing.

**Gate.** Any L1–L4 failure rejects the offending rows and reports them by `seedId`; more
than 5% rejected on L3 rejects the profile (the state-author is stuck on a template).

### I6 — the corpus is answerable

**Statement.** A competent reader given only the state block, and the tool list, must
produce the expected call. Everything above can pass on a corpus that is internally
consistent and externally meaningless.

**Procedure.** `corpus audit <profile>` draws a stratified sample of
`n = min(60, max(30, 8·k))` rows, allocated as evenly as the op counts allow (`--n` overrides,
and the override is recorded), ordered by `sha256(corpusSha ‖ rowId)` so the sample is
reproducible and independent of row order. At k = 4 that is 32 rows, 8 per op; at k = 8 it is
60, i.e. 7–8 per op. The auditor is a
**fresh subagent that has never seen a rationale, a seed, a region, or the generator's
prompts**; its packet is `tools[]` + `renderedState` + "which call, and would you send this
argument as-is?". For every sampled row it answers:

```
opMatch     0/1     did it choose the same op
argOk       0/1     would it send this argument as-is
underdetermined  0/1  the state did not determine one call
```

**Thresholds** (per profile, over the sample):

```
opMatch rate ≥ 0.90        and  Wilson 95% lower bound ≥ 0.80
argOk rate   ≥ 0.80
underdetermined ≤ 0.05
```

**Why Wilson and not the point estimate.** At n=30 the point estimate moves 3.3 points per
row, and at n=32 (k=4) 3.1; a corpus that reports 0.90 without an interval is reporting
noise. The interval is
published in `checks.json` and in every eval record that quotes the corpus
(`task-reframing.md` §4.6 makes this the label-noise number).

**Gate.** Any threshold failure rejects the profile. A pass with `argOk` between 0.80 and
0.90 is admitted and marked `answerability: "arg-weak"` in the manifest, which the eval
record carries — the argument is real work and an argument half the readers would rewrite is
a measurement, not a hidden defect.

### I7 — target hygiene

Not one of the six the brief names, but free and it closes two shortcuts.

```
∀ rows: |answers| == 1
∀ rows: answers[0].name == call.op  ∧  answers[0].arguments has exactly one key == argumentRules name
∀ rows: reasoning matches /^"(.{8,60})" -> [a-z_]+$/  and span ⊆ renderedState
∀ rows: reasoning and argument contain no token from lexicon.forbidden
∀ rows: renderedState contains no token from lexicon.forbidden with frequency
        > 0.15 of rows in any class, and (per token) class-conditional rates within ±0.15
∀ rows: max-len sanity — tokenCount(prompt+target) ≤ maxLen (§8.3)
```

The forbidden lexicon in the state is the "narration" guard: a state may describe a
situation, it may not name the operation. It is a rate check rather than a ban, because
real panes do sometimes contain such words and a corpus with none of them is not
representative.

**Gate.** The first four are zero-tolerance. The frequency clause is a report with a 0.15
cap.

### I8 — budget

```
∀ rows:  tokenCount(renderedPrompt + target) ≤ maxLen            (engine tokenizer)
p95 tokenCount(renderedPrompt) ≤ maxLen − 96                    (max_new_tokens headroom)
12 · ceil(R/16) · t_probe / 3600 ≤ 24 h                          (§4.3 gate)
```

`maxLen` is declared in the manifest per profile: the smallest power of two ≥
p95(prompt+target)+8, floor 512. `t_probe` is the probed step time at that `maxLen`.

### I9 — generator stability and provenance

```
relabel disagreement on a 5% sample ≤ 2%                       (§3.7)
every row has stateModel / labelModel / advModel / promptSha / at
corpusSha = sha256(rows.jsonl) recorded in the manifest
descriptorSha = sha256(role-grammars.json) recorded in the manifest
```

**Gate.** Any failure rejects the profile.

## 6. Generator bias, and the seven mechanisms that price it

A single model writing both states and labels produces a corpus shaped like its own priors:
the states it finds easy to write, labelled the way it is inclined to label them, with the
hard middle of the distribution missing. That corpus trains a model to imitate the
generator's taste and evaluates it on the same taste. Seven mechanisms, in the order they bite,
with the last one being the only one that proves the other six are doing anything:

### M1 — State and label are generated independently, by different agents, blind

The state-author never sees `tools[]`; the labeller never sees the seed, the region, or the
intended op (§3.2). The joint distribution is therefore the product of two independent
conditionals rather than one agent's opinion about which pairs belong together. This also
means the labeller can only use what the *state* says — which is precisely the deployment
task — so a state that underdetermines its call shows up as an adversary reject or auditor
underdetermination instead of as a silently confident wrong label.

Where independence is impossible — the labeller must see the state to label it — the check
on it is M3 and I3: if the state leaks the answer, the leak is measurable and fatal,
whichever agent wrote it.

### M2 — Adversarial rows: minimal pairs are a quota, not a hope

Per op, ≥ 12 admitted **minimal pairs**: a pair is two rows sharing `seedId` and differing
in exactly one field, where the labeller was re-run blind on both and produced *different*
ops. Construction: take an accepted row, ask the state-author to re-emit it with one field
mutated (a different `idleTicks` bucket, one error line added or removed, `phase` advanced),
and re-run labeller + adversary on the new state only.

Pairs are the rows that teach a boundary rather than a phrase: they make a one-field
shortcut *provably* insufficient (the fields are otherwise identical), and they are the rows
a 1-NN baseline gets wrong, which is why they interact with M5. Quota:

```
≥ 12 admitted pairs per op
≥ 50% of pairs have both members accepted (a pair with one member rejected is reported,
    never completed by inference)
pair members share a group key → they land on the same side of the split (§7)
```

### M3 — A held-out validator that never sees the generator's rationale

The adversary (§3.2) sees `tools[]`, the state, and the call — never the rationale, never
the seed, never the region. If the call only makes sense given the rationale, the state is
insufficient and the row is dropped. This is the per-row version of I6, and it is the one
place a subagent is allowed to gate an individual row.

A rationale is therefore **not** evidence of answerability; it is a record of what the
labeller thought, kept in `rows.jsonl` for the audit trail and **never rendered into the
training line** (the training target's reasoning is the terse `"<span>" -> <argname>`
form, §8.2 — both because that is the format the rest of the pipeline already speaks and
because a long prose rationale spends target tokens from a 96-token budget).

### M4 — Cross-model and cross-configuration validation

Two generator families, where a second is reachable:

- **Rows** are split between the families by `seedId` parity, never by region, so neither
  family owns a class.
- **Probe.** `corpus/_probes/<profile>.jsonl` — 100 states, generated once, never in
  train or val. Both families' labellers answer every probe state. Requirement:

```
per-op agreement between families ≥ 0.90     and     overall ≥ 0.90
```

Below that, the op's *definition* is model-dependent, which means it is not defined by the
grammar — a finding for `role-grammars.md`, and the profile is rejected with the
confusion matrix attached.

When only one model is reachable, the same test runs **cross-configuration**: two disjoint
prompt-construction variants (different ordering/persona of the same instruction set, and
disjoint samplers/temperatures), with the same 0.90 gate. The manifest records
`crossModel: "single-family (cross-config)"` and no record may describe the corpus as
cross-model validated. This is a degradation, and it is labelled as one rather than quietly
skipped.

### M5 — The dumb-baseline gate

Three baselines, computed on the **val** split, from the same code path that scores the
model (`bench/runners/metrics.ts` once it exists; a local equivalent in `corpus check`
until then). If a baseline that does no reasoning scores inside the band, the corpus is
degenerate:

| gate | baseline | must satisfy |
|---|---|---|
| **G1** | `always <modal op>` | `BA == q` exactly, `exactMatch == q ± 0.02` |
| **G2** | best single-field stump over `context` (I3a's max) | `BA ≤ q + 0.10` |
| **G3** | 1-NN, TF-IDF cosine over the whole `renderedState` | `BA ≤ 0.60` absolute |

G1 failing means the balance band broke. G2 failing is I3 failing, restated as a baseline.
**G3 is the anti-phrasebook gate**: if one nearest neighbour over lexical similarity can
answer 60%+ of a k-class corpus, the states are templates and the model will learn the
templates. It is a *ceiling*, deliberately loose — the corpus must not be a phrasebook, but
it must stay surface-separable, because this architecture selects surface evidence and
composes almost nothing (`task-reframing.md` §2.2). Both numbers are printed, and the low
side is read too: a 1-NN at the 0.60 cap is a phrasebook, and a 1-NN near chance means the op
is not visible in the surface tokens at all, which for this architecture means unlearnable
rather than hard. Only the high side gates, but a corpus below `q + 0.05` is flagged
`surfaceSignal: "absent"` in the manifest and its eval record says so before any fine-tune
is paid for.

### M6 — Generation diversity controls

- Batch interleaving: 24 seeds drawn round-robin across regions, never a whole region per
  batch (§3.5) — a region-contiguous batch produces 24 paraphrases of one situation.
- The last 5 accepted states for the profile are always in the state-author's context, with
  the instruction to differ from them.
- Argument diversity is measured, not requested: I1's `distinct normalizeArg ≥ 10`,
  `maxTemplateShare ≤ 0.20`, `distinct opener ≥ 5`, `distinct argument ≥ 40`.
- The seed pool is ≥ 2.5× `R`, so no seed is used twice and the pool itself cannot become
  the template.

### M7 — The checker has positive controls, or it is decoration

`corpus/_fixtures/` holds four deliberately broken corpora, and `corpus check --self-test`
must reject all four with the right invariant id. This is the only thing that makes the
leak check a test instead of a claim:

| fixture | constructed by | must fail |
|---|---|---|
| `_fixtures/leaky/` | take an accepted corpus; render `status: "working"` iff op ≠ leave, `intent: ""` iff op = leave — i.e. reproduce `dataset.ts:174-175` exactly; both fields stay `context`, which is what the mined descriptor would have had to declare them | **I3b** naming `status`/`intent`, **I3a**, **I3e**, and **I3d** on `idle` |
| `_fixtures/degenerate/` | 98% one op, 3 rows of another | **I2** and G1 |
| `_fixtures/nonspan/` | rewrite 5 arguments as paraphrases | **I4** |
| `_fixtures/shibboleth/` | keep a balanced corpus but make one token (a status word) uniform inside each class | **I3d** at `precision ≈ 1.0`, while I3a/I3b pass because the token lives in an `evidence` field |

The self-test runs in CI-equivalent form (`corpus check --self-test`) and after any change to
a check. A check that cannot fail on a corpus built to fail it is not a check.

## 7. The split

### 7.1 Rules

1. **Stratified on op.** Every op contributes `ceil(vf · n_c)` rows to val, `vf = 0.20`.
2. **Group-aware.** A row's group key is `pairId` when present, else `seedId`. All rows of a
   group go to one side. This is the fix for the 18% straddle probability the mined split
   carried (`task-reframing.md` §5.2: one session held 46 of 527 rows; a row-hash split put
   it on both sides 18% of the time), and here it is worse than in the mined corpus because
   minimal pairs are *deliberately* near-identical — a pair split across the boundary is a
   memorised val row.
3. **Reproducible by hash.** Groups are ranked by
   `sha256("corpus-split\0" ‖ profile ‖ "\0" ‖ groupKey)`, ascending, ties by groupKey. No
   RNG, no clock, no generator state.
4. **Allocation is a floor on the target, not a guarantee**, because a group cannot be split.
   Achieved `perOp` is published and I1's val floor (`0.2·C` per op, 32 rows at `C = 160`) is
   the gate.
5. **`valSha`** = `sha256` of the sorted val `rowId`s, one hex string. It is written into
   `split.json`, into `manifest.json`, and — this is the point — into every eval record's
   header.

### 7.2 `split.json`

```json
{"profile":"fetch-worker","seed":"corpus-split","vf":0.20,
 "rows":640,"groups":{"train":198,"val":51},
 "perOp":{"train":{"retry_fetch":128,"…":128},"val":{"retry_fetch":32,"…":32}},
 "valSha":"…","trainSha":"…","valRows":["sha256:…"],"trainRows":["sha256:…"]}
```

`eval.py` takes `--expect-val-sha` and exits non-zero on a mismatch. That is `task-reframing.md`
§5.1's V2 made mechanical, and it is the whole answer to the `d20`-on-`d4`-val bug: a rung
is scored on the val of the corpus it was trained on, and the corpus says which val that is.

### 7.3 Per-rung matched val sets

Because each profile has its own corpus, its own grammar and therefore its own trainer line
shape, **there is no shared val set and none may be manufactured**. The matrix:

| variant | trained on | scored on |
|---|---|---|
| `<profile>-d4`, `<profile>-d8`, `<profile>-d20` | `<profile>/train.jsonl` | `<profile>/val.jsonl` |
| `control-<profile>-d8` (no adapter) | — | `<profile>/val.jsonl` |

Every row of that table carries the same `valSha`. Comparing two profiles is not a thing
this spec permits: different grammar, different answer space, different state space. The
slate ranks within a profile; across profiles it reports, with `valSha` and `descriptorSha`
as headings, exactly as `slate.ts` already refuses to rank across SHAs.

## 8. Files, format, and the trainer contract

### 8.1 Where corpora live

```
corpus/
  _contract/
    row.schema.json                  §3.4
    profile.schema.json              §2.2's descriptor, for validation
  _fixtures/                         M7's four broken corpora, plus --self-test
  _probes/<profile>.jsonl            M4's 100 state probe states (never in train/val)
  <profile>/
    rows.jsonl                       authored rows, the source of truth
    rejects.jsonl                    every dropped row with reason + region (append-only)
    checks.json                      latest `corpus check` output, gates + measured values
    manifest.json                    counts, shas, model ids, epochs/maxLen/resolution
    audit/<batch>/packet.jsonl       the I6 sample as the auditor saw it
    audit/<batch>/verdicts.jsonl     the auditor's per-row answers + the tallies
    train.jsonl  val.jsonl           derived — regenerated, never hand-edited
    split.json                       §7.2
```

`corpus/` is authored; `finetune/out/` stays generated. `mine/out/` is untouched: the mined
archive is now a historical record and an input to nothing. Nothing in `corpus/` is
symlinked into `finetune/out/` — the converter reads `corpus/<profile>/rows.jsonl` and
writes `corpus/<profile>/train.jsonl`, and `finetune` is pointed at the result with a path
argument. One corpus, one directory, one sha.

### 8.2 The trainer line

`needle/model/finetune.py::render_example` reads exactly these keys:

```python
render_example(example):
    tools     = example.get("tools", [])          # str or list, json.dumps separators=(",",":")
    answers   = example.get("answers", …)         # str or list
    reasoning = example.get("reasoning") or ""    # optional, wrapped in THINK markers
    system    = example.get("system") or ""       # optional, own template block
    prompt = prefix + IM_START+"user\n" + TOOLS_START + tools_json + TOOLS_END + "\n"
             + example["query"] + IM_END+"\n" + IM_START+"assistant\n"
    target = think + TOOL_CALL_START + answers_json + TOOL_CALL_END + IM_END
```

So the factory emits, per row:

| key | value |
|---|---|
| `query` | the profile's `renderedState`, verbatim from `rows.jsonl` |
| `tools` | the profile's tool schemas as an **array**, serialized by the trainer with `separators=(",",":")`, `ensure_ascii=False` — byte-identical for every row of a profile |
| `answers` | `[{"name": op, "arguments": {argumentName: argument}}]` — exactly one element |
| `reasoning` | `"<span>" -> <argumentName>`, span ⊆ state, ≤ 60 chars |
| `system` | the profile's `system` text |

**The `system` decision, and why it is a deviation.** The mined corpus folds `SYSTEM` into
`query` (`dataset.ts` writes `query = SYSTEM + "\n\n" + renderInput(...)`) and leaves
`system` absent, while deployment sends `system=SYSTEM, user=renderInput(...)`
(`needle.ts:278`; the sidecar concatenates them as `system + "\n\n" + user`). That is one
train/infer mismatch of the D1 family. For the synthetic corpora the faithful form is the
one the template already has a slot for: **`system` carries the role's system text, `query`
carries only the state block.** The factory asserts `query` is byte-identical to
`rows.jsonl.renderedState`, so the check, the split and the trainer all read one string,
and the manifest records `renderConvention: "system-slot"` so a corpus can never be silently
compared to one built the other way. A profile's train and val use one convention; mixing
the two in one run is not permitted.

`finetune/tools.py` today hardcodes four op functions. Per-profile catalogues need one
`tools.py` per profile (or a `--profile` flag), and `dataset.ts`'s `ARGUMENT_NAME` map is
hardcoded to the four mined ops, so it cannot render these corpora. Both are downstream
changes this spec does not authorise (§11) — but they are the reason the factory writes the
trainer line itself rather than going through `dataset.ts`: the converter's job (mined row →
trainer line, with label mapping and `firstSentence` argument extraction) has no analogue
when the row is already authored in trainer shape. **The factory's converter is a renderer
and a splitter, not a labeler** — no label logic lives between `rows.jsonl` and
`train.jsonl`.

### 8.3 Token budget

`maxLen` per profile, from I8:

```
required  = p95(tokenCount(renderedPrompt + target))
maxLen    = smallest power of two ≥ required + 8, floor 512, cap 1024
```

The tokenizer is the authority (`needle`'s, in the venv), not a char estimate. The char
proxy (`dataset.ts`'s `maxExampleChars = 1850`) exists because the converter had no
tokenizer; the factory has one and must use it, and it must report `required`, `maxLen` and
the p50/p95 in `checks.json`. Setting `maxLen = 512` where the prompt fits is the ~2× of
§4.3 and is required, not optional, when the gate needs it.

## 9. The acceptance gate

A profile is **trainable** when every line below holds. `corpus accept <profile>` re-runs
`corpus check`, recomputes the gate table, and writes `accept.json`. `slate.py` refuses a
variant whose `accept.json` is absent or failing.

| # | gate | threshold | source |
|---|---|---|---|
| 1 | I1 coverage | `n_c ≥ C` (§4.1's per-op allocation, 160 when affordable), train `≥ 0.8·C`, val `≥ 0.2·C`, per op | §4.1 |
| 2 | I1 structure | `distinct normalizeArg ≥ 10`, `maxTemplateShare ≤ 0.20`, `distinct opener ≥ 5`, `distinct argument ≥ 40`, per op | §5 I1 |
| 3 | I2 balance | `n_c/n ∈ [0.80q, 1.20q]`, `max_c n_c/n ≤ 0.45`; `majorityBaseline` printed | §5 I2 |
| 4 | I3a leak (context) | `∀f ∈ context: BA_f ≤ q + 0.10` (5-fold CV, field family of §5 I3) | §5 I3 |
| 5 | I3b leak (context) | `∄(f,v,c), f ∈ context: support ≥ 12 ∧ precision ≥ 0.85 ∧ recall ≥ 0.15` | §5 I3 |
| 6 | I3d leak (lexical) | `∄(t,c) over all fields, unigrams and bigrams: support ≥ 12 ∧ precision ≥ 0.85 ∧ recall ≥ 0.15` | §5 I3 |
| 7 | I3e ablation (context) | `BA_all − BA_(-f) < 0.25` for every single `f ∈ context`; `BA_all` printed | §5 I3 |
| 8 | I4 span | 100% of accepted rows: `renderedState.includes(argument)`, 8–140 chars, rules met; ≤ 0.5% allowance on re-check | §5 I4 |
| 9 | I5 distinct | L1 = L2 = 0 violations; L3 ≤ 0.85 Jaccard (non-pair); L4 ≥ 0.95 per op | §5 I5 |
| 10 | I6 answerable | `opMatch ≥ 0.90` (Wilson LB ≥ 0.80), `argOk ≥ 0.80`, `underdetermined ≤ 0.05`, n ≥ 30 | §5 I6 |
| 11 | I7 hygiene | zero-tolerance clauses pass; forbidden-token rate ≤ 0.15 | §5 I7 |
| 12 | I8 budget | `≤ maxLen` for every row; `p95 prompt ≤ maxLen − 96`; `12 epochs ≤ 24 h` at probed `t_step` | §5 I8, §4.3 |
| 13 | I9 stability | relabel disagreement ≤ 2%; provenance complete | §5 I9 |
| 14 | M2 pairs | ≥ 12 admitted minimal pairs per op, ≥ 50% with both members accepted | §6 M2 |
| 15 | M4 cross | per-op family agreement ≥ 0.90 on the 100-state probe | §6 M4 |
| 16 | M5 baselines | G1 `BA == q`; G2 `BA ≤ q + 0.10`; G3 `BA ≤ 0.60` (flag `surfaceSignal: "absent"` below `q + 0.05`) | §6 M5 |
| 17 | manifests | `corpusSha`, `descriptorSha`, `promptSha`, `valSha`, `resolution`, `renderConvention`, model ids, the `evidence`/`context` partition all present | §2.2, §7, §3.7, §8.2 |
| 18 | self-test | `corpus check --self-test` rejects all four `_fixtures/` with the right invariant ids | §6 M7 |
| 19 | resolution | `resolution` is `"0.60-vs-0.50"` (val ≥ 30/op) or the profile is marked `provisional` and no per-op claim may be quoted from it | §4.2, §4.4 |

### 9.1 What to do when a corpus fails

The remediation is per gate and never editorial. The rules:

| failing gate | allowed remediation | forbidden |
|---|---|---|
| I1 coverage / structure | more seeds in under-served regions; more template variety in the seed prose | dropping rows from a fat op to "help" balance |
| I2 balance | re-allocate the seed pool (§3.5) | relabelling a row; duplicating a minority row |
| I3a, I3b, I3e (context leaks) | change the **state schema** (add the missing field, widen an enum, remove the field carrying the answer) and regenerate; or fix the renderer | editing individual states until the number passes; re-partitioning a field to `evidence` to silence I3a |
| I3d (lexical leak) | re-edit the seed prose so the shibboleth is not the situation; or move the discriminator into a second field | adding a synonym list to the lexicon so the token "does not count" |
| I4 span | re-generate the offending rows; if systematic, the argument rule in the descriptor is wrong | paraphrasing an argument by hand |
| I5 distinctness | more seed regions; re-emit the duplicate group | keeping the near-duplicates and raising the Jaccard cap |
| I6 answerable | re-generate the ambiguous regions; check the op definitions against the state space | loosening the threshold |
| I7 hygiene | fix the generator packet | leaving a "narration" token in because the rate was under the cap |
| I8 budget | trim the prefix / set `maxLen` from the measurement / 8 epochs with `epochsOverride` | dropping `C` below `C_min` (§4.1) |
| I9 stability | re-write the op's definition — a flapping label is a definition problem | averaging the two labels |
| M2 pairs | build the pairs explicitly | inferring the second member's label |
| M4 cross-model | **stop.** The op is model-dependent: escalate to `role-grammars.md` | choosing the family whose numbers look better |
| M5 baselines | the corpus is degenerate: back to I1, I2 or I3 | declaring "the baseline is unfair" |
| manifests, self-test | fix the manifest / the checker | — |

**Two failures and the profile goes back to the grammar.** A profile that fails the same
gate twice has a definitional problem, not a generation problem, and the third attempt is
wasted money. The corpus directory is kept (`corpus/<profile>/rejected/<utc>/`) so the
finding has evidence attached, and the report names the gate and the two attempts' measured
values.

**A hand-edited row is a new row.** If anyone edits a row by hand — including to fix a
typo — it must be re-run through I3–I7 and the adversary, and the audit sample is re-drawn.
There is no "obviously fine" edit; the historical leak was two lines that looked fine.

## 11. What this spec does not do

- **No rows are generated here.** This file authorises nothing. It defines the protocol, the
  invariants, the thresholds and the file layout; the first corpus is a separate change.
- **No grammar, state field, op or value is invented here.** §2 defines the descriptor the
  factory reads and refuses to run without; `role-grammars.md` is the content.
- **No mining.** `mine/` is untouched and is not an input. Its archive stays as the
  historical record and the source of the numbers in §1. Real captured states are not used
  for train, val, probes, or fixtures in v1; if a later pass wants them, the only permitted
  use is a diagnostic probe outside `corpus/`, and this spec would be amended first.
- **No source change.** Everything below is required for the factory to run end to end, and
  is listed so the next change has a work list, not an authorisation:
  - `finetune/tools.py` → one catalogue per profile (or `--profile`), byte-identical to the
    descriptor's `tools`;
  - `finetune/dataset.ts` → `ARGUMENT_NAME` cannot serve a per-profile grammar; the factory
    does not use this converter at all (§8.2);
  - `finetune/eval.py` → `--expect-val-sha`; `finetune/slate.py` → per-profile variants and
    a gate on `accept.json`;
  - `bench/runners/metrics.ts` → G1–G3 as the shared implementation, so §6 M5 and the
    recorded metronomes cannot diverge;
  - `src/labeling/label-to-op.ts` → unaffected: these corpora have no mined label, so
    `LABEL_TO_OP` is not in their path. `TASK_OPS` per profile comes from the descriptor.
- **No claim that a model can learn these corpora.** §4 sets the floors that make learning
  *possible*; whether 121M attention-only parameters clear `BA_lo > 0.500` on a balanced
  five-op corpus is the measurement, not a promise.
- **No Ollama, no local LLM runtime outside the trainer.** The generation models are
  whatever the profile's tier provides; the fine-tune is `needle` on CPU.

## 12. Acceptance checks for the factory itself

Runnable, with expected outcomes a reviewer can check by hand. These test the *factory*,
not a corpus; until they pass, no corpus may be accepted.

1. **Descriptor gate.** `corpus check fetch-worker` with no `role-grammars.json` → exit
   non-zero, message naming the missing descriptor, zero rows generated.
2. **Positive controls.** `corpus check --self-test` → four fixtures, four rejections, each
   naming its invariant: `_fixtures/leaky` → `I3a`, `I3b` (`status`, `intent`), `I3d`
   (`idle`), `I3e`; `_fixtures/degenerate` → `I2`, `G1`; `_fixtures/nonspan` → `I4`;
   `_fixtures/shibboleth` → `I3d` only, with I3a/I3b/I3e passing. A fixture that passes
   means the checker is broken, not the fixture. The `shibboleth` fixture is the important
   one: it is the only one that proves I3d reaches into `evidence` where a stump does not.
3. **The historical leak is reproducible as a failure.** Building `_fixtures/leaky` with
   `status: point.humanText ? "working" : "idle"`, `intent: point.humanText` must produce
   `I3b` with `precision = 1.000, recall = 1.000` on both (`status`=`idle`) and
   (`intent`=`""`). If the numbers come out lower, the check is reading a different
   rendering than the trainer does — which is itself a D1-class bug.
4. **Split determinism.** `corpus split <profile>` twice → byte-identical `split.json` and
   `valSha`. Shuffling the line order of `rows.jsonl` and re-splitting → same `valSha`.
5. **No group straddle.** For `<profile>`: `groups.val ∩ groups.train = ∅`, no `pairId`
   appears on both sides, and every pair's two members sit on the same side of the split.
6. **Span gate bites.** Take any accepted row, prefix its argument with two words that are
   not in the state, re-run `corpus check` → `I4` fails naming that `rowId`.
7. **The leak gate is specific, and only fires where it should.** Three passes over one
   accepted corpus, because a gate that fires on "any field that matters" would forbid every
   real signal:
   (a) permute a `context` field that carries nothing (`pane`, an opaque id) → no I3
       failure;
   (b) permute a `context` field that *is* load-bearing in combination (`phase`) → still no
       I3a/I3b failure. If I6's `opMatch` drops, that is the measurement showing the field
       matters, which is allowed and is not a leak;
   (c) set `phase` to a function of the op → I3b fires naming `phase`, and I3e reports
       `BA_all − BA_(-phase) ≥ 0.25`. The two must agree; a corpus where I3b fires and I3e
       does not means the association is not load-bearing for a linear baseline, and the
       gate message should say so rather than leave the reader to reconcile it.
8. **Baselines reproduce arithmetic.** G1 prints `BA == q` and `exactMatch == q` to three
   decimals for the balanced corpus. On `_fixtures/degenerate` it prints `BA == q` and
   `exactMatch ≈ 0.98`, i.e. accuracy and BA disagree — which is the whole reason the gate
   is on BA.
9. **Budget gate is measured, not assumed.** `corpus check <profile>` prints
   `p50/p95 prompt tokens`, `maxLen`, and `12 epochs ≤ 24 h` using a `t_step` it took from a
   probe of *that* file. A run that quotes 262.4 s/step for a 512-length profile is wrong.
10. **The acceptance artifact is complete.** `accept.json` contains all 19 gate rows of §9
    with measured values and thresholds, `corpusSha`, `descriptorSha`, `promptSha`,
    `valSha`, `resolution`, `renderConvention`, the `evidence`/`context` partition, and the
    three model ids. `slate.py` exits non-zero on a variant whose `accept.json` is stale
    relative to `corpusSha`.

## 13. One-line summary

Five role profiles, each with its own grammar (from `role-grammars.md`), its own `C·k`
authored rows (160 per op where the wall clock allows it, and the shortfall stated rather
than hidden), and its own sha'd val set. States are written by an agent that has never seen
the tool list; labels by an agent that has never seen the seed; both are checked by code that
must fail on four deliberately broken corpora before it may pass anything. Nine invariants,
nineteen gate rows, and one number that matters: a classifier over any single `context` field,
or over any single token, must stay at chance — and a corpus where it does not is rejected
rather than trained on.
